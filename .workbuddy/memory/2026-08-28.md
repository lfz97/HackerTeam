## 评估：Captain 是否引入 trpc-agent-go 的 todo 工具（tool/todo）

- 背景：链接 https://trpc-group.github.io/trpc-agent-go/zh/tool/#todo ，讨论是否给队长 agent 加 `todo_write`。
- 结论：值得加基础版 `todo.New()`（建议性），**不要**用 `agent/extension/todoenforcer`；需自定义 `WithClearOnAllDone(false)` + 自定义 nudge，并在 captain.md 给出「PTES 阶段 ↔ todo 条目」映射规则（质量复核不通过保持 in_progress；最终报告为最后一条）。
- 关键事实（已核实 pinned 版本 v1.11.1-0.20260820131707 源码）：
  - 清单存 session.State（`temp:todos[:branch]`），不占 message 历史，不受 ContextCompaction / 摘要影响；但框架**不会**把清单自动注入上下文，模型只能看到最近一次 todo_write 的 tool result，该结果被压缩后会重新规划（漂移风险）。
  - 默认 `WithClearOnAllDone(true)`：全部完成即清空，不利于 Captain 收尾阶段引用。
  - 校验：todos 必填数组、最多一个 in_progress、content 唯一。
- 副作用待办：TUI 侧 `service/engine/tools/parammapper.go` 需为 `todo_write` 加 mapper，否则无 mapper 的工具会原样打印完整 JSON 入参+结果，造成刷屏。
- 上下文：Captain 一次 run 内步数多（Recon→Scanner→Exploit→PostExploit→Reproducer×2→最终报告），prompt 已有硬编码 pipeline，最长跑偏的是「质量复核」和「第 8 步最终报告」。
- 备选方案（未采纳为主方案）：让 Captain 维护 `TASK_PLAN.md`，零依赖可归档，但缺 nudge 回灌、模型写完易忘读。
